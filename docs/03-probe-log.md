## What `pane.zoom` actually does, and to whom (throwaway `kampr-probe-265`, real herdr 0.8.2)

The operator, verbatim: *"i dont even get what zoom at the desk is aha"*, and a previous reading
that its effect is invisible in Kampr. Both halves of that are wrong, and the reason is a
distinction nothing in the log had drawn: whether a desk client is attached. Driven with
`research/probe/rpc.py` against `herdr server --session kampr-probe-265`, and then again with a
real `herdr --session kampr-probe-265` forked under a PTY at 200x60 — **with every `HERDR_*`
variable stripped from the child**, because nested herdr is refused by default and the first three
attempts measured a client that had printed *"nested herdr is disabled by default"* and exited.

| # | Claim | How | Result |
|---|---|---|---|
| 265 | **`pane.zoom` really does resize the PTY, but only with a client attached — and the layout rect never moves either way, so the only pane geometry that follows a zoom is `scroll.viewport_rows`, and only when the split was vertical** | one workspace, one right split and one down split, `pane.zoom on`/`off` against each; `stty size` written to a file from inside each pane, `session.snapshot` rects and `pane.list` `scroll.viewport_rows` read either side; repeated headless and against a real 200x60 client | **Headless: nothing moves at all.** The PTY never followed the split in the first place (#68/#84) so there is nothing for a zoom to move: rect `47x40`, PTY `93x40`, unchanged through `on` and `off`, and `changed: true, zoom_changed: true` returned each time. **Attached, right split:** PTY `84x58` → **`171x58`** → `84x58`, while the rect stays `87x60` and `viewport_rows` stays `58` **in all three states**. **Attached, down split:** PTY `171x28` → **`171x57`** → `171x28`, rect stays `174x30`, and `viewport_rows` moves `28` → **`57`** → `28`. So the rect is fiction during a zoom exactly as it is in a headless session, and `viewport_rows` is honest exactly as [#84](#) found — it is the PTY's rows and not the rect's — but it says nothing about columns, and nothing on the socket does ([#221](#)) |

Which settles what a phone sees, without a new live test — and a new live test is why this is a
probe row rather than one. **`live.rs` runs headless**, so a zoom test there would drive an op that
cannot move a PTY, and would go green with the whole width path deleted: a harness that was never
the app ([#191](#)). What the chain is made of is already measured:

- **A down-split zoom is seen immediately.** `observe_geometry` takes rows from
  `scroll.viewport_rows`, the snapshot sweep notices `28 → 57`, `Stop::GeometryChanged` fires and
  the observer respawns at the new height. Guarded end to end by the width-following live tests.
- **A right-split zoom is seen by the width poll, and by nothing else.** Nothing in the snapshot
  moves, so `Stop::GeometryChanged` cannot fire — but herdr **re-wraps the pane the instant it is
  zoomed**, with no new output: the same 300-column logical line read back as rows of `84` before
  the zoom and rows of **`171`** after it, from a pane nobody had typed into. That is [#85](#)'s
  proof, so `probe_width` proves the new width on its next tick and `Stop::WidthChanged` restarts
  the stream. `width_poll` is **3 s**, which is the lag an operator is looking at, and it is the
  same poll-only story as a desk resize ([#52](#)).
- **A pane with no wrapped line has no proof**, and falls back to `max(rect, floor)` — the rect
  being the frozen pre-zoom one. It cannot crop content, because the floor is the widest row
  actually rendered and can only widen the stream, but the pane will not use its new width until
  something on it wraps.

**The naming, which is what the operator actually hit.** Kampr already has a control called Zoom —
the magnification of the rendered grid, in the pane header, announced as *"Zoom, currently 1.6x"* —
and the actions sheet offered a second chip called `zoom`, one screen away, for an unrelated herdr
op, with *"at the desk"* carrying the entire distinction. The sheet's chip is now **`fill the tab`**.

## Still open

- ~~A client that reconnects gets no withdrawal, because the node has no memory of what it is
  holding.~~ **Answered by the page rather than by the node ([#264](#)):** `convo` carries an
  additive `fresh`, because a node that restarts cannot remember what any client holds however the
  memory is keyed. What is *not* closed is an older phone, which ignores the field and merges — the
  additive rule buys forward compatibility, not a retrofit.
- ~~A relayed pane hands a joining watcher a grid and a scrollback, and no conversation.~~
  **Fixed ([#263](#)):** every joiner wanting the transcript re-asks the peer, and the hub marks
  the first page it hands each client. The hub still shadows no conversation, so the page costs one
  crossing of the WAN per joiner — cheap because it is the same ask a first watcher already makes,
  and worth re-measuring if a pane ever gets many simultaneous viewers.
- **`a_turn_in_progress_streams_off_the_screen_and_yields_to_the_record` is load-sensitive.** One
  failure in a full-workspace run, then 3 of 3 alone and green in every full run since. `Watch::
  observe` emits a fresh `Change::Show` whenever the previewed text *advances*, so a pane repaint
  racing the appended record produces a second non-empty preview and the test asserts on the first
  one it sees after the append. The mechanism is in the test's window, not in the pump. Left alone
  deliberately; re-run it alone before calling it a regression.

- ~~Does `pane.read recent` with `lines > viewport_rows` scroll a pane with a *detected agent*?~~
  **No — measured, and the interlock has dropped its agent clause (#231).** A live `codex` and a
  live `claude`, both herdr-detected and both holding a ring, answer `lines: 5000` in **1 ms** with
  every row of the ring, `truncated: false`, and `offset_from_bottom`/`max_offset_from_bottom`
  exactly where they were; a pane deliberately marked an agent while running a mouse-mode program
  received no wheel bytes at all, so herdr does not go near the agent’s scroll interface. What *is*
  slow is a live harness whose ring is **empty** — Claude Code clears the scrollback when it takes
  the screen — where every read past `viewport_rows` costs a flat ~375 ms and returns the viewport
  anyway. That is the case `max_offset_from_bottom > 0` already excludes, so it is the only half of
  the interlock left. The premise underneath the old half had also stopped being true: agent panes
  were said to be alt-screen with no ring to miss (#30), and a codex pane read back 402 rows.
- **A real mid-range ARM phone.** #56 is emulator-only; the shaping cost is the part that will move.
- **What a real *phone* browser reports for `hover` and `pointer` ([#266](#)).** The desktop half
  is now measured and closed — [#267](#) is an operator's own desktop answering `[true, false, 10]`,
  which both confirms the media query on real hardware and shows why the touch count could not be
  the question. The phone row is still the specification rather than a measurement, held as a table
  in `BrowserKeyboardTest`; nothing on this machine can be made into one, and letting the harness
  pick the predicate is exactly the defect #266 records.
- ~~Why herdr’s headless rect is one column wider than the PTY it created (#69).~~ **The rect is
  the pane’s outer box and the column it keeps back is the scrollbar’s (#230).** Rendered and read
  off the screen: on a 120-column client the single unbordered pane’s rect is 94 at `x: 26`, its
  content occupies columns 26–118, and column 119 holds `▕` — the scrollbar. Split, each pane
  loses three columns and two rows to its box border plus that same gutter. The gutter is reserved
  whether or not a scrollbar is being drawn, which is why the headless rect is one wider with no
  visible reason.
- ~~How to make the width proof in #211 safe.~~ **Closed.** `pane.read` has no offset and no way
  to ask for the logical lines *of* a set of rows, so the two reads cannot be made one window at
  the API. They are reconciled in the node instead: walked from the bottom, where both are
  anchored on the same row, pairing each logical line with the rows that rebuild it. The
  wide-glyph residual is closed too: a break a double-width glyph made is carried as the pair of
  widths it is and settled against what the pane has already proved, rather than resolved upwards
  on the spot. What cannot be closed is a pane that has never shown a narrow break at all — a
  92-column PTY of wide glyphs and a 93-column one read back byte for byte the same (#220), and
  nothing else on the socket reports a column count (#221) — and that pane is observed at the
  wider of its two candidates, whose extra column no wide glyph could have reached.
- ~~Whether a double-width cell should occupy two cells on the wire or carry a width flag
  (#210).~~ **Answered: two cells in the grid, a per-run `w` on the wire.** The premise of the
  question was wrong — the node's grid was *not* faithful to herdr's cell model. Herdr spends two
  columns on a wide glyph and addresses the next one at col+2, so a grid that spends one disagrees
  with herdr, and that disagreement is the whole of #210. `State::put` now advances by
  `unicode-width` and writes a tail cell, and the wire carries `w` (1 or 2, omitted when 1) rather
  than a sentinel character, so `x` stays exactly the text on screen for copy, find and link
  detection. See `docs/04-wire-protocol.md`.
- ~~**A long interactive prompt can silence the width poll entirely.**~~ **A defect, and fixed —
  but not in the walk’s stop rule (#229).** The ~1900-column line is real and reproduces exactly: a
  1787-column write on a 93-column pane came back as one logical line of **1891** columns over rows
  of 92, eighteen of 93, then the remainder. `rebuilds()` could not reconstruct it because it laid
  every row of a join out at one stride, and one row was a column short — a double-width glyph will
  not straddle the last column, so herdr laid that row out at 92 and the join carries it as 92. The
  rows of a join do not all occupy the same width, so the grid cannot be divided out of the total;
  what the total *does* pin down is the pair the grid must be one of, `p / n` and `p / n + 1`, and
  both are now tried. A grid only one of them rebuilds is proved outright by the rows that filled
  it; a grid both rebuild is exactly #220’s ambiguity. Across 80 live screens at a PTY held to 93
  and 80 more at 92, the old rule measured nothing on **32** of them and the new rule on **3**,
  with no wrong width from either. **Skipping the line was rejected**: a line that cannot be rebuilt
  is a line whose height is unknown, so there is no count of rows to step over with it, and every
  join above it would then be paired with rows that are not its own — which is #211, the defect the
  walk exists to prevent. The stop stays.
- **A dropped keystroke does not say which of two things went wrong.** `KamprConnection.send`
  refuses a keystroke on two different grounds — the socket is not live, which is the deliberate
  rule that a half-typed command must not be replayed into a live shell a reconnect later, and
  `outbox.trySend` failing because the 64-message buffer is full while the socket *is* live, which
  means the writer is suspended in `session.send` behind a stalled link. Both land on
  `noteInput(pane, delivered = false)` and both surface as the same "Not sent · N" badge, so the
  badge cannot distinguish "there is nowhere to put this" from "the writer is behind". Nothing is
  measured here: the second case needs a real stalled link and a run of typing longer than the
  buffer to reach at all, and it has never been observed. Telling them apart needs a reading of
  whether the pump is making progress — the count queued and the age of the oldest entry when the
  refusal happens — which is a state the connection does not keep today. Left alone deliberately:
  the buffer is what bounds the backlog, and an unbounded one would trade a visible refusal for a
  silent delay. If the badge is ever reported from a phone, this is the first thing to instrument.
