## Brief
Symptom: a fresh pi pane (no prompts, no tool running) renders the conversation and title of whatever pi session is active in the same cwd. Mechanism (scout-verified): in crates/kampr-journal/src/adapter.rs Registry::locate (349-386), pi always misses handle 2 (no held fd, no breadcrumb; the env handle exists only while a tool runs, #542), so handle 3 (cwd fallback, 377-385) fires; newest_declaring (discover.rs:145-170) excludes transcripts that STOPPED before the pane started, not one a neighbour is still writing, so the foreign transcript is served. The sticky() doc (adapter.rs:161-170) exists to forbid exactly this: 're-resolving by directory would latch onto whoever ran last in it'; pi is the only sticky harness (omp/mod.rs:440-442). Fix: in Registry::locate, skip the locate_by_cwd fallback when the adapter is sticky — a sticky harness whose process handle named nothing returns Ok(None): empty conversation, no title (the 'answers nothing rather than answering wrongly' rule). omp is non-sticky and its process handle succeeds first, so it is unaffected. Verify the pump (convo.rs:351-371) and herd model (state.rs:500-578) sticky blocks need no change (they already key on journals.sticky). TDD: integration-level tests — (a) sticky harness, cwd holds an actively-written foreign transcript, fresh pane with no env handle -> locate returns None; (b) sticky harness with its env handle present -> resolves its own session; (c) non-sticky harness cwd fallback still resolves. Prove load-bearing: reverting the fix fails the tests. House rules: zero comments by default; #NNN are probe-log citations; no wire change.
